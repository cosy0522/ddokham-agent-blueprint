# 세팅 프롬프트 형식

`설계도/세팅_프롬프트.md`의 형식이다. 다음 세션에 그대로 붙여 넣는 프롬프트이므로, 설명이나 머리말 없이 프롬프트 본문만 담는다.

이 프롬프트는 **만드는 단계**의 지시다. 설계는 이미 끝났고, 다음 세션은 실제로 물건을 만든다.

---

## 0. 두 가지 큰 원칙

### 원칙 1 — 프롬프트는 혼자 서야 한다

**외부 파일을 하나도 못 읽어도 프롬프트만으로 끝까지 갈 수 있어야 한다.** 기획서와 설계도와 서식 파일은 보강용이다.

설계 값을 프롬프트 본문에 글자로 박아 넣는다. "기획서를 읽고 규칙을 따르라"가 아니라 규칙을 그대로 적는다.

| 본문에 반드시 박아 넣는 것 | 빠뜨렸을 때 벌어진 일 |
|------------------------|-------------------|
| 지켜야 할 규칙 (머릿속규칙 + 지시요지 둘 다) | 남이 만든 것 같은 결과가 나온다 |
| 다 됐다고 볼 기준 | 언제 끝인지 몰라 끝나지 않는다 |
| 이번에 만들 단계와 안 만들 단계 (번호와 이름) | "이번 범위만 만들라"가 가리키는 대상이 없다 |
| 만들 파일의 이름과 둘 자리 | 사람마다 파일이 흩어진다 |
| 켜진 부품이 하는 일 | 설계도에서 켠 것이 세팅에 나타나지 않는다 |
| 보내는 수단과 받는 사람 | 마지막에 무엇으로 보낼지 지어낸다 |

한쪽만 옮기는 사고가 실제로 났다. `구성.지시요지`만 옮기고 `입력.머릿속규칙`을 통째로 빠뜨린 프롬프트가 나갔다. **두 목록은 항상 함께 옮긴다.**

### 원칙 2 — 세팅 단계는 만드는 단계다

**"폴더를 새로 만들지 말 것" "설정 파일을 만들지 말 것"을 이 프롬프트에 넣지 않는다.**

초기화 금지는 설계 단계(인터뷰 스킬)의 규칙이다. 세팅 프롬프트는 폴더도 파일도 당연히 만든다. 만들지 말라고 적으면 만들 수가 없다.

| 단계 | 폴더·파일을 만드나 |
|------|-----------------|
| 설계 단계 — 인터뷰 스킬 | 만들지 않는다. `설계도/` 안 파일 세 개가 전부다 |
| 세팅 단계 — 이 프롬프트 | 만든다. 폴더·정의 파일·화면 파일을 다 만든다 |

---

## 1. 폴더는 세 이름으로만 부른다

프롬프트 안에서 `폴더`라는 말을 홀로 쓰지 않는다. 어느 폴더인지 끝까지 안 정해지면 파일이 흩어진다.

| 이름 | 무엇이 들어 있나 | 누가 채우나 |
|------|---------------|-----------|
| 설계도 폴더 | `설계도/` — 기획서.md · 설계도.html · 세팅_프롬프트.md | 이미 있다 |
| 자료 폴더 | 서식 파일 · 지난번 완성본 · 시험에 쓸 자료 한 건 | 사람이 준비물대로 채운다 |
| 작업 폴더 | 이번에 만드는 것 | 다음 세션이 만든다 |

세 폴더는 모두 지금 열려 있는 폴더 아래에 둔다.

### 갈래별 실제 이름

| 갈래 | 자료 폴더 | 작업 폴더 |
|------|---------|----------|
| 스킬 | `자료/` | `스킬/{이름}/` |
| 도구 | `자료/` | `도구/` |
| 에이전트 | `구성.폴더` 중 참고 자료를 두는 폴더. 없으면 `자료/` | `구성.폴더` 전부 + `.claude/` |

정한 이름을 프롬프트 처음부터 끝까지 똑같이 쓴다. 준비물에 `참고자료/`라고 적었으면 작업 절차에서도 `참고자료/`다.

## 2. 블록 구조

블록은 넷이다. 이 순서를 바꾸지 않고 이름도 바꾸지 않는다.

```markdown
# 준비물
# 목표
# 참고할 것
# 작업 절차
```

### 왜 준비물이 맨 앞인가

**준비물만 사람이 읽는 블록이고 나머지 셋은 다음 세션의 AI가 읽는 블록이다.** 사람이 읽을 것을 맨 위에 둔다.

붙여 넣은 뒤에 무엇을 준비했어야 하는지 알게 되면 이미 늦다. 서식 파일을 폴더에 가져다 두는 일은 붙여 넣기 전에 끝나야 한다.

`기획서에 "고정참조: 서식 파일"이라고 적힌 것`과 `그 파일이 실제로 폴더에 있는 것`은 다른 일이다. 준비물 블록이 그 둘을 잇는다.

### 블록별 규칙

| 블록 | 규칙 |
|------|------|
| `# 준비물` | 첫 줄은 사람에게 하는 안내 한 줄. 그 아래에 폴더별로 둘 파일을 이름으로 적는다. 마지막 줄은 없을 때 어떻게 하는지 한 줄 |
| `# 목표` | 존댓말 한 문장 지시로 시작한다. 하위 불릿은 셋. 첫 두 줄은 갈래가 달라도 같고 셋째 줄만 갈래별로 다르다 |
| `# 참고할 것` | 이름표가 붙은 묶음으로 적는다. 묶음 순서를 고정한다 |
| `# 작업 절차` | 번호 매긴 6~10개. 1번은 준비물 점검, 마지막은 넘겨주기 |

### 참고할 것의 묶음 순서

```
읽을 파일
{갈래}의 생김새
지켜야 할 규칙
다 됐다고 볼 기준
이번에 만들 단계
이번에 안 만들 단계
만든 것을 두는 곳
```

`읽을 파일`은 없을 때 어떻게 하는지를 줄마다 붙인다. `{갈래}의 생김새`는 만들 물건이 무엇인지 모르는 채로 시작하지 않게 하는 묶음이다.

## 3. 문장 규칙

| 규칙 | 내용 |
|------|------|
| 목표 첫 문장 | 존댓말 한 문장. `~해 주세요`로 끝낸다. 이 한 문장만 존댓말이다 |
| 불릿과 절차 | 동사형 또는 `~할 것`으로 끝낸다 |
| 강조 금지 | 별표를 쓰지 않는다 |
| 한 문장 한 줄 | 문장 중간에서 줄을 바꾸지 않는다 |
| 불필요한 지시 금지 | `한국어로` `친절하게` `전문가처럼` 같은 말을 넣지 않는다 |
| 폴더 이름 | 1절의 세 이름으로만 부른다 |
| 확인 문장 | 무엇을 보여 주고 무엇을 묻는지 같이 적는다 |
| 하위 불릿 | 갈림길과 먼저 물을 것에만 쓴다. 한 절차에 두 줄까지 |
| 빈 값 | 채울 값이 없으면 그 줄을 통째로 뺀다. 중괄호를 남기지 않는다 |

### 쓰는 말

이 프롬프트는 다음 세션의 AI에게 주는 지시다. 설계도는 풀어 쓴 말을 쓰지만 프롬프트는 원래 용어를 쓴다.

| 써도 되는 말 | 쓰지 않는 말 |
|------------|------------|
| 스킬, SKILL.md, 담당 파일, 화면 파일, 아이콘 파일 | 스키마, 렌더, 파싱, 프롬프트 엔지니어링 |
| 설계도 폴더, 자료 폴더, 작업 폴더, 결과 파일 | 배포 파이프라인, 인스턴스, 런타임, 서버 |

### 바꿔 쓰는 말

왼쪽은 실제로 나갔다가 알아듣지 못한 문장들이다. 오른쪽으로 바꾼다.

| 쓰지 않는 말 | 대신 쓰는 말 |
|------------|------------|
| 처리 순서를 한 단계씩 붙이고 | 이번에 만들 단계를 하나씩 넣고, 하나를 넣을 때마다 시험용 자료로 결과를 확인할 것 |
| 확인받을 것 | {만든 것}을 보여 준 뒤 {물을 것}을 물을 것 |
| 어떤 값이 어디로 옮겨 가는지 정리해 보여줄 것 | 자료의 어느 항목이 결과물의 어느 자리로 들어가는지 표로 보여 줄 것 |
| 링크만 열어도 보이는지 확인할 것 | 파일을 두 번 눌러 열리는지 확인할 것 |
| 실행 명령을 안내할 것 | 파일을 두 번 눌러 열게 만들 것 |
| 단계마다 확인받을 것 | 절차마다 만든 것을 보여 준 뒤 다음으로 넘어갈지 물을 것 |

## 4. 작업 절차 규칙

| 규칙 | 내용 |
|------|------|
| 개수 | 6개 이상 10개 이하 |
| 한 절차는 한 가지 일 | 한 문장으로 적는다. `그리고`로 두 가지 일을 잇지 않는다 |
| 중복 금지 | 같은 일을 두 절차에 적지 않는다. 뒤 절차는 `{번호}번에서 정리한 것`으로 가리킨다 |
| 묻는 것이 먼저 | 이름과 설명을 정하는 절차는 본문을 쓰는 절차보다 앞에 둔다 |
| 보여 주는 것이 먼저 | 만든 것을 보여 주고 묻는 절차는 고치는 절차보다 앞에 둔다 |
| 저장 자리 명시 | 파일을 만드는 절차는 파일 이름과 둘 자리를 그 문장 안에 적는다 |
| 멈추는 지점 | 기준과 대조해 고치는 절차는 두 번까지 고치고 세 번째에는 남은 차이를 적어 알리고 멈추게 한다 |

### 열 개를 넘을 때

부품 문장 중 **이번에 만들 단계에 걸리지 않는 것부터 뺀다.** 이번 범위 밖 단계에만 붙는 부품은 애초에 넣지 않는다. 뺀 부품은 기획서의 「다음 단계」로 옮긴다.

### 무한 반복을 막는 문장

기준과 대조하는 절차는 이 형태로 쓴다.

```
다 됐다고 볼 기준과 하나씩 대조해 어긋난 곳만 고칠 것 — 두 번 고쳐도 남으면 남은 차이를 적어 알리고 멈출 것
```

무엇을 고치는지(어긋난 곳만)와 몇 번 만에 멈추는지(두 번)가 한 문장에 있어야 한다.

## 5. 데이터가 들어가는 자리

| 프롬프트 자리 | 데이터 |
|------------|-------|
| 목표 첫 문장 | `이름` · `갈래.판정` |
| 준비물 — 자료 폴더에 둘 것 | `입력.고정참조[].이름` · `결과물.이름` · `입력.매번바뀜[0].이름` |
| 읽을 파일 | 설계도 폴더 두 파일 + 자료 폴더 파일 이름 |
| 지켜야 할 규칙 | `입력.머릿속규칙` + `구성.지시요지` — 둘 다 옮긴다 |
| 다 됐다고 볼 기준 | `결과물.완성기준` |
| 이번에 만들 단계 | `범위.이번에만들것` + `과정[].이름` |
| 이번에 안 만들 단계 | `범위.다음에` + `과정[].이름` |
| 만든 것을 두는 곳 | 1절 갈래별 작업 폴더 · `구성.폴더` |
| 작업 절차 1번 갈림길 | `미정` |
| 사람이 볼 지점 절차 | `구성.사람확인지점` |
| 부품 문장 | `부품` 중 `쓴다: true`인 것 |
| 보내는 수단·받는 사람 | `부품.보내기연결.내용` · `결과물.받는사람` |
| 멈추는 조건 | `부품.평가담당.기준` · `부품.평가담당.종료조건` |

### 규칙과 지시요지를 합치는 법

두 목록을 한 목록으로 적는다. 문구가 글자까지 같은 줄만 하나로 줄인다. 비슷하다고 지우지 않는다. 하나라도 빠뜨리면 만들어도 쓸모가 없다.

### 값이 비었을 때

값이 비면 그 줄을 뺀다. 중괄호가 남은 프롬프트가 나가면 붙여 넣은 사람이 그대로 실행한다.

`미정` 배열이 비어 있지 않으면 작업 절차 1번 아래에 하위 불릿 한 줄을 넣는다.

```
- {미정 항목}을 먼저 물을 것
```

## 6. 갈래별 완성 틀

세 갈래는 블록 구조가 같고 본문이 다르다. 중괄호가 채우는 자리다.

### 스킬 갈래

```markdown
# 준비물
붙여 넣기 전에 지금 열려 있는 폴더에 아래를 둔다.
- 설계도/ — 기획서.md와 설계도.html이 들어 있는 설계도 폴더
- 자료/ — 아래 파일을 복사해 두는 자료 폴더
  - {입력.고정참조[].이름} — 서식 파일 그 자체
  - {결과물.이름} 지난번 완성본 한 건
  - {입력.매번바뀜[0].이름} 한 건 — 시험에 쓸 자료
없는 것이 있어도 그대로 붙여 넣는다. 첫 절차에서 무엇이 없는지 알려 준다.

# 목표
아래에 적힌 대로 {이름} 스킬 하나를 만들어 주세요.
- 자료 폴더의 실제 파일을 열어 서식과 항목을 확인할 것
- 한 절차씩 진행하고, 절차마다 만든 것을 보여 준 뒤 다음으로 넘어갈지 물을 것
- 스킬 폴더 하나와 그 안의 SKILL.md 하나로 끝낼 것

# 참고할 것

읽을 파일
- 설계도/기획서.md — 무엇을 왜 만드는지. 없으면 이 프롬프트만으로 진행할 것
- 설계도/설계도.html — 흐름과 부품 구성. 없으면 건너뛸 것
- 자료/{입력.고정참조[].이름} — 항목 이름과 표 구조와 문체를 여기서 가져올 것
- 자료/{결과물.이름} 완성본 — 다 만든 것이 어떤 모양이어야 하는지 여기서 확인할 것

스킬의 생김새
- 폴더 하나와 그 안의 SKILL.md 파일 하나가 스킬의 전부다
- SKILL.md 맨 위에 이름과 설명을 적는다. 이름은 폴더 이름과 같게 하고, 설명에는 언제 쓰는 스킬인지를 한 문장으로 적는다
- 그 아래 본문에 무엇을 어떤 순서로 하는지와 지켜야 할 서식을 적는다
- 서식 파일이나 예시가 필요하면 같은 폴더에 함께 둔다

지켜야 할 규칙
- {입력.머릿속규칙 각 항목}
- {구성.지시요지 각 항목}

다 됐다고 볼 기준
- {결과물.완성기준 각 항목}

이번에 만들 단계
- {번호}. {단계 이름}

이번에 안 만들 단계
- {번호}. {단계 이름}

만든 것을 두는 곳
- 스킬/{스킬 이름}/SKILL.md

# 작업 절차
1. 자료 폴더에 무엇이 있는지 확인하고, 없는 파일이 있으면 무엇이 없는지 알린 뒤 어떻게 할지 물을 것
```

## 7. 부품이 켜졌을 때 넣는 문장

기획서에서 `씀`으로 적힌 부품만 문장을 넣는다. 안 쓰는 부품은 프롬프트에 아무 말도 넣지 않는다. 안 쓰는 이유는 기획서에만 남는다.

**이번에 만들 단계에 걸리지 않는 부품은 켜져 있어도 넣지 않는다.** 이번에 안 만들 단계에만 붙는 부품은 이번 세팅의 일이 아니다.

| 부품 | 넣는 문장 | 넣는 자리 |
|------|---------|----------|
| 서식·절차 스킬 (에이전트) | `{형식}을 다루는 부분은 이미 있는 {형식} 스킬을 쓰고 새로 만들지 말 것 — 없으면 .claude/skills/{스킬 이름}/SKILL.md로 만들고 2번에서 정리한 서식을 그 안에 적을 것` | 지시를 적는 절차 뒤 |
| 서식·절차 스킬 (스킬 갈래) | `결과물을 {형식}으로 내보내는 부분은 이미 있는 {형식} 스킬을 쓰게 하고, SKILL.md 본문에 그 스킬을 쓴다고 적을 것` | 본문을 적는 절차 뒤 |
| 나눠서 동시에 | `{담당 이름들} 담당 파일을 .claude/agents/ 안에 하나씩 만들고, 각 담당이 어디서 무엇을 가져오는지 그 파일에 적을 것` | 단계를 적는 절차 뒤 |
| 평가 담당 | `평가 담당 파일을 .claude/agents/평가담당.md로 만들고, {평가담당.기준}을 보게 하고 {평가담당.종료조건}이면 멈추게 적을 것` | 초안을 만드는 절차 뒤 |
| 보내기 연결 | `결과물을 {결과물.받는사람}에게 {보내기연결.내용}으로 보내는 연결을 붙이고, 보내기 전에 보낼 내용을 보여 준 뒤 보낼지 물을 것` | 시험하는 절차 앞 |
| 혼자 도는 도구 | `두 번 눌러 실행되는 아이콘 파일을 화면 파일 옆에 만들고, 다른 PC에서도 두 번 눌러 열리는지 확인할 것` | 화면을 확인하는 절차 뒤 |
| 보여주는 페이지 | `{보여주는페이지.내용}을 한 화면으로 보여 주는 파일을 만들고, 그 파일을 두 번 눌러 열리는지 확인할 것` | 시험하는 절차 뒤 |

문장을 넣으면 뒤 번호를 다시 매긴다.

### 보내기 연결에는 하위 불릿을 붙인다

무엇으로 보내는지와 주소를 어디서 가져오는지가 없으면 마지막에 지어낸다. 연결이 안 될 때의 갈림길도 함께 넣는다.

```
- 보내는 수단과 받는 사람 주소를 어디서 가져올지 먼저 물을 것
- 연결이 안 되면 보낼 내용을 파일로 만들어 두고 어디에 있는지 알려 줄 것
```

### 갈래별로 넣을 수 있는 부품

| 갈래 | 넣을 수 있는 문장 |
|------|-----------------|
| 스킬 | 서식·절차 스킬 (스킬 갈래용 문장) |
| 도구 | 혼자 도는 도구, 보여주는 페이지 |
| 에이전트 | 여섯 개 전부 |

### 조건이 붙는 문장

| 조건 | 하는 일 |
|------|--------|
| 부품.스킬 내용이 `docx` `xlsx` `pptx` `pdf` 같은 흔한 문서 형식 | 이미 있는 스킬을 쓰라고 적는다. 새로 만들라고 적지 않는다 |
| 부품.스킬 내용이 그 밖의 용도 | `{용도} 스킬을 새로 만들 것`으로 적는다 |
| 혼자도는도구가 `로컬 웹앱` | 아이콘 파일 문장을 넣지 않는다. 도구 틀에 이미 들어 있다 |
| 혼자도는도구가 `실행 파일` | 아이콘 파일 문장을 넣고 뒤에 `화면 파일로 안 되는 이유는 {웹앱으로안되는이유}다`를 붙인다 |
| 보내기연결이 꺼져 있음 | 준비물의 받는 사람 주소 줄을 뺀다. 보낼 일이 없으면 준비할 것도 없다 |
| 평가담당의 종료조건이 비어 있음 | `세 번 왕복`을 넣는다. 비운 채로 내보내지 않는다 |
| 범위.다음에가 비어 있음 | 이번에 안 만들 단계 묶음을 통째로 뺀다 |

| 넣지 않는 문장 | 왜 |
|-------------|-----|
| 폴더나 설정 파일을 새로 만들지 말 것 | 초기화 금지는 설계 단계의 규칙이다. 세팅 단계는 만드는 단계다 |
| 작업 폴더를 만들지 말고 끝낼 것 | 위와 같다. 만들 자리가 없으면 만들 수가 없다 |
| 실행 명령을 안내하고 마칠 것 | 쓰는 사람이 명령어를 치는 일은 없다 |
| 계정에 올리는 절차를 적어 준 문장 | 확인되지 않은 절차는 지어낸 것이 된다. 강사 안내를 따르라고만 적는다 |
| 매번 같은 서식과 절차를 스킬로 분리할 것 (스킬 갈래에서) | 만들 것 자체가 스킬 하나다. 분리할 대상이 없다 |
| 링크만 열어도 보이는지 확인할 것 (도구 갈래에서) | 내 PC에서 여는 파일에는 링크가 없다 |
| 확인받을 것 / 진행할까요 | 무엇을 보여 주고 무엇을 묻는지가 없어 같은 질문만 반복된다 |
| 기준에 맞는지 확인할 것 (멈추는 지점 없이) | 어긋난 것을 몇 번까지 고치는지가 없어 끝나지 않는다 |

## 9. 같은 본문을 한 번 더 넣는다

여기서 만든 본문을 데이터의 `세팅프롬프트`에 문자열로 그대로 넣는다. 설계도의 복사 버튼이 이 값을 쓰기 때문에 두 곳의 내용이 같아야 한다.

`세팅_프롬프트.md` 파일에는 이 본문만 담고, 설명이나 제목 줄을 위에 붙이지 않는다. 붙여 넣는 사람이 지우는 수고를 하게 된다.

## 10. 내보내기 전 확인

프롬프트를 다 쓴 뒤 아래를 하나씩 본다. 하나라도 아니면 고친 뒤 내보낸다.

혼자 서는가
- 지켜야 할 규칙에 머릿속 규칙과 지시로 적을 것이 둘 다 들어갔는가
- 다 됐다고 볼 기준이 본문에 글자로 적혔는가
- 이번에 만들 단계가 번호와 이름으로 적혔는가
- 켜진 부품이 전부 작업 절차 문장으로 나타났는가
- 설계도 폴더의 두 파일이 없어도 끝까지 갈 수 있는가

블록과 문장
- 블록이 준비물·목표·참고할 것·작업 절차 넷이고 순서가 맞는가
- 준비물에 자료 폴더에 둘 파일이 이름으로 적혔는가
- 목표가 존댓말 한 문장이고 불릿이 셋인가
- 폴더를 부를 때 설계도 폴더·자료 폴더·작업 폴더 중 하나로만 불렀는가
- 중괄호가 남아 있지 않은가
- 별표 강조가 없는가

작업 절차
- 절차가 6개 이상 10개 이하인가
- 한 절차가 한 가지 일인가
- 같은 일이 두 절차에 겹치지 않는가
- 정하는 절차가 쓰는 절차보다, 보여 주는 절차가 고치는 절차보다 앞에 있는가
- 파일을 만드는 절차마다 파일 이름과 둘 자리가 적혔는가
- 기준과 대조하는 절차에 멈추는 지점이 적혔는가
- 확인하는 문장에 무엇을 보여 주고 무엇을 묻는지가 적혔는가

- 스킬 갈래 — 계정에 올리는 절차를 지어내지 않고 강사 안내를 따르라고 적었는가

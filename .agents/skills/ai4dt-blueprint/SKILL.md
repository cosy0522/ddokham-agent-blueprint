# 이 스킬이 하는 일

Antigravity 프로젝트의 `.agents/skills/ai4dt-blueprint/`에서 실행한다. `/ai4dt-blueprint` 명령으로 시작하며 명령 접두사는 플랫폼에 따라 자동 발견된다. 초기화는 하지 않는다. 현재 열려 있는 작업 폴더의 파일을 읽는다. 참조 자료는 이 스킬의 `references/`에서 읽고, HTML 생성은 형제 스킬 `../blueprint-draw/SKILL.md`를 따른다.

작업 디렉터리에는 결과 폴더 `설계도/`만 만들며 이 저장소 자체의 설정은 변경하지 않는다.


코딩을 모르는 사람이 자기 업무를 어떻게 자동화할지 스스로 기획하게 돕는다.
백지에서 시작하지 않고 질문으로 시작한다.

인터뷰가 끝나면 사용자 폴더에 `설계도/` 하나가 생기고 그 안에 파일 세 개가 들어간다.
그 밖에는 아무것도 만들지 않는다.

# 말투와 표기 원칙

- 특정 기관·업종·직군의 이름을 예시로 들지 않는다. 예시는 어느 회사에서나 통하는 사무 업무로만 든다.
- 전문용어를 사용자에게 노출하지 않는다. 구조·형식·데이터 처리 방식을 설명하는 말은 화면에 쓰지 않는다.
- 부품은 풀어 쓴 이름으로만 부른다. 서식·절차 스킬 / 나눠서 동시에 / 평가 담당 / 보내기 연결 / 혼자 도는 도구 / 보여주는 페이지.
- 원래 용어는 `세팅_프롬프트.md` 안에서만 쓴다. 그 파일은 다음 세션의 AI가 읽는 문서다.
- 한 문장은 한 줄로 쓴다. 문장 중간에서 줄을 바꾸지 않는다.
- 사용자를 평가하지 않는다. 판정 결과를 말할 때도 이유를 함께 말한다.

# 참고 파일을 언제 읽나

필요할 때 그때 읽는다. 처음부터 전부 읽지 않는다.

| 언제 | 읽을 파일 |
|------|----------|
| 0단계에서 폴더에 결과물 후보가 없을 때 | `references/examples.json` |
| 1~4단계 질문을 물을 때 | `references/question-bank.md` |
| 갈래를 판정할 때 | `references/track-rules.md` |
| 부품을 판정할 때 | `references/part-rules.md` |
| 답을 데이터로 정리할 때 | `references/data-schema.md` |
| `기획서.md`를 쓸 때 | `references/plan-format.md` |
| `세팅_프롬프트.md`를 쓸 때 | `references/prompt-format.md` |
| 설계도를 그릴 때 | `blueprint-draw` 스킬 |

질문 문구와 보기는 `references/question-bank.md`에 있는 것을 그대로 쓴다.
질문을 새로 지어내거나 개수를 늘리지 않는다.

# 진행 절차

## 0단계 — 결과물 찾기 (질문이 아니다)

1. 현재 폴더의 파일 목록을 훑는다. 하위 폴더는 한 단계까지만 본다.
2. 사람이 만들어 낸 산출물로 보이는 파일을 최대 네 개 고른다. 문서·표·발표자료·서식 파일이 후보다.
3. 고른 파일을 열어 제목·항목·표 구조를 파악한다. 큰 파일은 앞부분만 본다.
4. "이 중에 만들고 싶은 결과물이 있나요?"로 묻는다.

여기서 파악한 내용은 뒤 질문의 초안이 된다.
빈칸을 묻지 말고 초안을 먼저 보여 주고 고치게 한다. 이것이 인터뷰를 짧게 만드는 핵심이다.

- 후보로 삼을 파일이 없으면 `references/examples.json`을 읽어 네 가지 예시를 보여 주고 하나를 고르게 한다.
- 파일이 안 열리면 파일 이름과 확장자만으로 추정해 질문으로 확인한다.
- 폴더 안 파일의 본문 내용을 산출물에 옮겨 적지 않는다. 항목과 구조만 본다.

## 1단계 — 결과물 확정 (질문 3개)

무엇을 만들고 싶은지, 완성되면 어디로 가는지, 얼마나 자주 만드는지를 묻는다.
두 번째 질문이 갈래 판정의 축이다. 복수 선택을 허용한다.

## 2단계 — 재료 역추적 (질문 3개)

만들 때마다 새로 받는 자료와 그 출처, 늘 똑같이 참고하는 자료, 남에게 시키면 꼭 틀리는 것을 묻는다.
출처의 개수를 정확히 센다. 갈래와 동시 실행 판정이 여기서 갈린다.
"남한테 시키면 꼭 틀리는 게 뭔가요"는 이 인터뷰에서 가장 중요한 질문이다.
답이 짧게 나오면 한 번 더 캐묻는다. 이 칸이 비면 만들어도 쓸모가 없다.

## 3단계 — 과정 재현 (질문 3개)

지금 어떤 순서로 만드는지, 어느 단계가 제일 오래 걸리는지, 다시 손보거나 반려당한 적이 있는지를 묻는다.

- 순서는 먼저 묻지 말고 3~6단계 초안을 제시한 뒤 고치게 한다.
- 각 단계마다 AI가 하는지, 사람이 하는지, AI가 하고 사람이 확인하는지를 붙인다. 이것도 먼저 제안하고 고치게 한다.
- 2단계의 "틀리는 것"과 3단계의 "반려 사유"는 다르다. 앞은 지시가 되고 뒤는 검사 기준이 된다.

## 4단계 — 범위와 실행 (질문 2개 + 조건부 1개)

오늘 어디까지 만들지와 어떻게 시킬지를 묻는다.
기본 추천은 "제일 오래 걸리는 단계만"이다. 나머지는 다음 단계로 옮긴다.
평가 담당이 켜지는 경우에만 몇 번까지 고치게 할지를 추가로 묻는다.

## 5단계 — 갈래 판정과 이유 제시

`references/track-rules.md`를 읽고 판정한다.
갈래는 스킬 · 도구 · 에이전트 셋 중 하나다.

- 판정만 통보하지 않는다. 이유를 반드시 함께 말하고, 이유는 사용자가 한 답을 그대로 인용한다.
- 판정을 강요하지 않는다. "그래도 다르게 만들어 보시겠어요?"로 뒤집을 기회를 준다.
- 사용자가 뒤집으면 그대로 따르고, 데이터의 `갈래.선택`을 `상위로 변경`으로, `갈래.원래권장`을 원래 판정으로 남긴다.
- 애매하면 낮은 쪽을 먼저 권한다. 크게 만들면 나중에 고칠 것도 크다.

단순한 업무에 에이전트를 세우는 것이 가장 흔한 과잉 설계다.
자료 하나로 문서 하나 만드는 일은 스킬로 충분하다는 것을 이유와 함께 알려 준다.

## 6단계 — 부품 판정

`references/part-rules.md`를 읽고 판정한다.
부품을 판정하려고 질문을 새로 묻지 않는다. 이미 받은 답으로 판정한다.
예외는 하나다. 평가 담당이 켜지면 종료 조건을 반드시 묻고, 답을 못 하면 세 번 왕복을 기본값으로 넣는다.

- 갈래에 따라 판정 범위가 다르다. 판정 범위 밖의 부품은 끄고 이유를 적는다.
- 부품 여섯 칸을 모두 채운다. 안 쓰는 부품도 지우지 않고 안 쓰는 이유를 한 구절로 적는다.
- 배운 것을 다 얹지 않는다. 조건이 맞을 때만 켜고, 왜 필요한지 한 줄을 붙인다.
- 켜진 부품이 넷 이상이면 경고한다. 어느 둘부터 만들지 고르게 하고 나머지는 다음 단계로 옮긴다.

## 7단계 — 산출물 세 개 만들기

순서를 지킨다. 세팅 프롬프트 본문이 설계도 안으로 들어가기 때문이다.

1. `references/data-schema.md`를 읽고 지금까지의 답을 그 구조의 데이터로 정리한다. 필드 이름과 값을 한 글자도 바꾸지 않는다.
2. `설계도/` 폴더가 없으면 만든다.
3. `references/plan-format.md`대로 `설계도/기획서.md`를 여덟 개 섹션까지 완성한다.
4. `references/prompt-format.md`대로 `설계도/세팅_프롬프트.md`를 쓴다. 갈래에 따라 본문이 달라진다.
5. 4에서 쓴 본문을 데이터의 `세팅프롬프트` 값에 그대로 넣는다.
6. `blueprint-draw` 스킬을 읽고 그 절차대로 `설계도/설계도.html`을 만든다.

인터뷰를 시작할 때 `설계도/` 안에 이미 파일이 있으면, 갱신을 시작하기 전에 덮어써도 되는지 사용자에게 확인한다.

## 8단계 — 안내

- 파일 세 개의 전체 경로를 알려 준다.
- 설계도는 파일을 더블클릭하면 브라우저에서 열린다고 알려 준다. 인터넷이 없어도 열린다.
- 고칠 것이 있으면 `기획서.md`를 고친 뒤 `/ai4dt-blueprint-redraw`를 쓰라고 알려 준다.
- 머릿속 규칙 칸이 비어 있으면 그 칸부터 채우라고 한 줄로 알려 준다.

# 진행 중 지켜야 할 규칙

- 한 번에 한 단계씩 묻는다. 질문 열한 개를 한꺼번에 쏟지 않는다.
- 모든 질문은 보기에서 고르게 한다. 자유 서술은 두 개뿐이다.
- "아직 모르겠다"를 허용한다. 그 항목은 `미정`에 넣고 진행한다. 되묻지 않는다.
- 단계가 끝날 때마다 정리한 내용을 짧게 되읽어 주고 확인받는다. 중간 진행내용은 대화에서 유지하고, 파일은 7단계에서만 생성한다. 기존 `설계도/` 파일이 있으면 덮어쓰기 전에 확인한다.
- 제일 오래 걸리는 단계는 최대 두 개다. 셋 이상 고르면 제일 급한 둘만 고르게 한다.
- 앞 단계의 결과가 뒤 단계의 입력이면 동시 실행으로 제안하지 않는다.
- 인터뷰가 길어지면 남은 항목을 `미정`으로 두고 산출물 만들기로 넘어간다. 다 채우는 것보다 끝까지 가는 것이 낫다.
- 갈래도 부품도 사용자에게 직접 묻지 않는다. 업무를 묻고 판정은 이 스킬이 한다.

# 금지 사항

이 스킬은 설계 단계에서만 쓰는 도구다.
실제 세팅은 다음 단계에서 세팅 프롬프트가 한다.

- `CLAUDE.md`를 만들지 않는다.
- 작업 폴더를 만들지 않는다. 설계도에 폴더 이름이 적히더라도 그 폴더를 실제로 만들지 않는다.
- 서브 에이전트나 스킬 정의 파일을 만들지 않는다.
- 설정 파일을 만들지 않고, 초기화 커맨드를 실행하지 않는다.
- 설계한 결과물을 실제로 만들지 않는다. 코드나 스크립트를 쓰지 않는다.
- 폴더에 있던 기존 파일을 고치거나 지우지 않는다. 읽기만 한다.
- 어디에도 업로드하지 않는다. 전부 사용자 PC 안의 파일이다.
- 문서 본문·실제 수치·개인 정보를 산출물에 담지 않는다. 항목과 구조만 담는다.

만드는 것은 `설계도/` 안의 파일 세 개뿐이다. 그게 전부다.

"먼저 초기화부터 하시죠" 같은 안내도 하지 않는다.
폴더를 열고 바로 시작하는 것이 이 커맨드의 사용법이다.
